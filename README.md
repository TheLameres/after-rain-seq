# after-rain-seq

Генеративный MIDI-хост для Ambient Dub Techno: гармонический движок (лад, войсинги,
аккордовый граф), drum-машина (евклидовы ритмы, 16 lane GM), непрерывная мутация
паттернов — с управлением с Ableton Push 2 или из терминала. Работает на Raspberry Pi 5
(Raspberry Pi OS 64-bit, Ubuntu) и на macOS.

- **Клок:** три источника с переключением на лету — internal, MIDI Clock, Ableton Link
- **Порты:** обнаружение MIDI-устройств по имени, hot-plug, перенаправление в рантайме
- **CC-автоматизация:** логические имена параметров → номера CC, троттлинг 30 Гц
- **REPL:** мониторинг и контроль из терминала (удобно по SSH с RPi)

## Требования

- Python ≥ 3.13
- [uv](https://docs.astral.sh/uv/) — управление зависимостями
- MIDI-бэкенд: `python-rtmidi` (входит в зависимости)
- Опционально: Ableton Link — `uv sync --extra link`

## Быстрый старт

```bash
uv sync                      # установить зависимости
uv run python -m src.main --list-ports        # какие MIDI-порты видит система
uv run python -m src.main                     # headless-режим (config.yaml создастся сам)
uv run python -m src.main --simulate          # без железа (эмулятор Push 2)
uv run python -m src.main --repl              # + интерактивный терминал
```

Полный список флагов: `--config FILE`, `--log-level LEVEL`, `--log-layer NAME=LEVEL`
(повторяемый, Spring Boot-стиль), `--simulate`, `--list-ports`, `--repl`,
`--script FILE`.

## Конфигурация

При первом запуске рядом с `--config` (по умолчанию `config.yaml` в корне проекта)
создаётся файл с дефолтами. Все секции валидируются pydantic: ошибка в конфиге —
понятное сообщение и выход, движок с невалидным конфигом не стартует.

### `logging`

```yaml
logging:
  level:
    root: INFO
    src.sync: DEBUG        # per-layer override, ключи — имена логгеров
```

Уровни: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `OFF`.
CLI `--log-level` и `--log-layer` перекрывают эти значения на один запуск.

### `sync` — клок и транспорт

```yaml
sync:
  enabled: true
  clock_source: "internal"   # internal | midi | link (стартовый источник)
  midi_clock_device: null    # имя входного MIDI-порта для MIDI Clock;
                             # null — взять из env ISOBAR_DEFAULT_MIDI_IN
  bpm: 120.0                 # 20..300 — для internal и link
  swing_amount: 0.0          # 0.0..1.0, свинг длительностями (не wall-clock)
```

Переключение источника в рантайме (кнопкой или командой `clock source midi`)
квантуется на ближайшую долу и сопровождается `all_notes_off` — без разрыва фазы.

### `ports` — MIDI-порты ⭐

См. раздел «Настройка портов» ниже.

### `cc_map` — логические имена CC

```yaml
cc_map:
  default:                   # глобальный маппинг: имя → номер CC
    filter: 74
    resonance: 71
    reverb: 91
    delay: 93
    delay_feedback: 94
    mod_wheel: 1
    volume: 7
    pan: 10
  ports:                     # переопределения и опции per-port
    "Синт A":
      filter: 22             # тот же параметр — другой CC на этом порту
      cutoff:                # полный вариант: CC + инверсия + диапазон
        cc: 74
        invert: true
        range: [20, 110]
    "LCXL3":
      _no_automation: true   # не слать CC-автоматизацию на этот порт вообще
```

Генераторы шлют автоматизацию по именам (`filter`, `resonance`, …). Резолвинг:
переопределение порта → `default` → ошибка при загрузке конфига. Поверх маппинга
работает троттлинг 30 Гц по ключу `(порт, канал, CC)` — DIN-шина не забивается.

### `drum` — drum-машина

```yaml
drum:
  preview_on_select: true    # предпрослушка lane при выборе
  preview_velocity: 100      # 1..127
  mutate_min_seconds: 8.0    # интервал мутации паттерна, сек (1..120)
  mutate_max_seconds: 16.0   # (1..300)
```

### `mutation` — эволюция паттернов

```yaml
mutation:
  enabled: true
  mutate_min_seconds: 8.0    # 1..120
  mutate_max_seconds: 16.0   # 1..300
  default_mutate: 0.5      # стартовое значение mutate для новых дорожек (0..1)
  drift_step_gate: 0.05      # макс. смещение gate за одну мутацию (0..0.5)
  drift_step_density: 0.1    # макс. смещение density
  drift_step_register: 1.0   # макс. смещение register (полутона)
```

Мутация обратима: `freeze` замораживает текущее состояние одной кнопкой,
деградация возвращает паттерн к базовому рисунку.

## Настройка портов

Проект оперирует **логическими лейблами**, которые резолвятся в физические
MIDI-порты системы. Дорожки ссылаются на лейблы, а не на имена устройств —
замена железа не требует правки сессии.

### Как происходит обнаружение

1. По `match` (регистронезависимая подстрока) порту ищется в списке имён
   системных портов.
2. Совпадение одно → порт **connected**.
3. Совпадений несколько → если задан `serial`, среди них ищется подстрока
   серийника. Не помогло — статус **ambiguous** с явным сообщением
   (никогда не угадываем).
4. Ничего не найдено → **disconnected** — дорожки на этом порту молчат,
   сессия продолжает работать.

Hot-plug: порты опрашиваются каждые ~2 с — устройство подключилось, дорожки
оживли; отключилось — `all_notes_off` и тишина.

### Пример: выход на синтезатор

```yaml
ports:
  outputs:
    - label: "main"          # как дорожки ссылаются на порт
      match: "IAC Bus 1"     # подстрока имени системного порта
      role: melodic          # melodic | drum | clock
      serial: null           # нужен только при неоднозначном match
      no_automation: false   # true — не слать сюда CC-автоматизацию
  inputs:
    - label: "clock-in"
      match: "IAC Bus 2"     # источник MIDI Clock
      role: clock
```

Смотреть, какие имена видит система: `uv run python -m src.main --list-ports`.
На macOS для тестов включите IAC Driver (Audio MIDI Setup → MIDI Studio →
IAC Driver, создайте шину) — имена шин появятся в выводе.

### Пример: несколько синтезаторов с похожими именами

```yaml
ports:
  outputs:
    - label: "synth-a"
      match: "USB MIDI"      # оба устройства матчатся…
      serial: "A12"          # …serial выбирает нужное
    - label: "synth-b"
      match: "USB MIDI"
      serial: "B77"
```

Если `serial` не задан и match неоднозначен — порт получит статус `ambiguous`,
а в поле `error` будет список кандидатов: добавьте `serial`.

### Правила ролей и автоматизации

- `role` — метка для человека и будущих экранов Push 2; на маршрутизацию
  MIDI сейчас не влияет.
- `no_automation: true` — для контроллеров типа Launch Control XL 3,
  которым CC от генераторов не нужен.
- Drum-дорожки шлют на канал 10; мелодические — на свои каналы дорожек.

### Рантайм: переключение без рестарта

В REPL (`--repl`):

```
ars> ports                    # текущее состояние всех лейблов
ars> ports scan               # принудительный rescan
ars> ports switch main "USB MIDI"   # перенаправить лейбл на другое устройство
```

`ports switch` меняет только память процесса: `config.yaml` не трогается,
после рестарта восстановится конфиг. Заявка применяется на ближайшем
poll (~2 с): старый порт закрывается с `all_notes_off`, новый открывается.
`serial` при switch очищается — новое устройство, новый дизамбигуатор.

### Маршрутизация дорожек

Дорожки привязываются к портам-лейблам (не к физическим устройствам):

```
ars> track add pad
ars> track route "Pad 1" main      # подключить к порту (имена с пробелами — в кавычках)
ars> track route "Pad 1" aux       # переключить: старый порт глушится all_notes_off
ars> track unroute "Pad 1"         # отключить — тишина, сессия живёт
ars> track delete "Pad 1"          # удалить вместе с движком
```

- Лейбл валидируется по сконфигурированным портам — опечатка не пройдёт.
- Если у дорожки, добавленной после старта, ещё нет движка — `route`
  создаёт его автоматически (on demand).
- Маршрутизация — рантайм-only: в `config.yaml` не пишется.
- Drum-дорожки шлют на канал 10, мелодические — на канал дорожки.

### Диагностика

| Симптом | Причина | Действие |
|---------|---------|----------|
| Порт `disconnected` | Устройство выключено / имя не совпало | `--list-ports`, поправить `match` |
| Порт `ambiguous` | Несколько устройств подходят | Добавить `serial` |
| Дорожка молчит | Её порт не connected | `ports`, проверить статус лейбла |
| CC не доходят | `no_automation: true` или не тот CC | `cc_map:` для этого лейбла |

## REPL

`uv run python -m src.main --repl` — строчный терминал (prompt_toolkit):
живой статус-бар (~2 Гц), история команд, автодополнение. Основные команды:

Удобно по SSH с Raspberry Pi. Изменения — только рантайм, конфиг не пишется.

## Модификации на лету: цепочка этапов

У каждой дорожки есть **цепочка модификаций** — упорядоченный набор этапов,
через которые проходят ноты паттерна перед планированием. Этапы неизменяемы
и не хранят состояния между применениями; пустая цепочка — тождество (звук
как раньше). Цепочка живёт на дорожке: при создании дорожка копирует цепочку
профиля, а профили реестра (`pad`, `bass`, …) дают пустую цепочку —
модификации opt-in. Публикуемые в граф гармонии аккорды и копии событий
источников через цепочку не проходят — гармония соседей не меняется.

Доступные этапы:

| Этап | Параметры | Что делает |
|------|-----------|------------|
| `arpeggiate` | `step` (beats, default `0.25`, > 0), `direction` (`up`/`down`/`updown`, default `up`) | Разворачивает одновременные ноты (аккорд) в арпеджио: одна нота за шаг, длительность каждой равна шагу; на следующий аккорд не залезает |
| `densify` | `density` (`0.0`–`1.0`, **обязателен**) | Прореживает по позиции шага: `1.0` — без прореживания, `0.0` — ~25%; акцент на beat 0 не удаляется никогда |

Контракт: **Densify — до этапов, дробящих время**. Решение о прореживании
принимается по целым битам; после арпеджиатора все ноты первого такта
схлопываются в один индекс — такой порядок не запрещён, но решение
деградирует (поведение документировано и зафиксировано тестом).

### REPL

```
track chain <name> show | add <stage> [k=v ...] | remove <n>   # n — с единицы
```

```
ars> track chain "Pad 1" show
track "Pad 1": chain = — (empty)
ars> track chain "Pad 1" add arpeggiate step=0.25 direction=up
track "Pad 1": chain = arpeggiate step=0.25 direction=up
ars> track chain "Pad 1" add densify density=0.5
track "Pad 1": chain = arpeggiate step=0.25 direction=up → densify density=0.5
ars> track chain "Pad 1" remove 1
track "Pad 1": chain = densify density=0.5
```

Имена дорожек с пробелами — в кавычках. Ошибки (неизвестный этап — с перечнем
доступных, неизвестный или нечисловой параметр, значение вне диапазона, индекс
вне `1..len`) выводятся с кодом 1 и не прерывают цикл REPL; цепочка при
ошибке не меняется. Автодополнение подсказывает имена дорожек после
`track chain`, действия `show|add|remove` следующим токеном и имена этапов
после `add`.

### Семантика

- Замена цепочки подхватывается **со следующего тика**, без ожидания границы
  ступени: запланированные вперёд ноты старой цепочки снимаются и
  перестраиваются по новой, уже звучащие ноты доигрывают.
- Drum-дорожки цепочку игнорируют: операция вернёт **успех с
  предупреждением** (`drum — цепочка игнорируется (спецификация не
  применена)`), спецификация не применяется, цепочка остаётся пустой.
- Макро-ось DEN (прореживание в генераторе) и этап `densify` в цепочке —
  два независимых механизма: у дефолтных профилей цепочки пустые, двойного
  прореживания нет; комбинация DEN + `densify` — осознанный выбор
  пользователя.

### Скрипт

Тот же фасад доступен скриптам — плоские обёртки над движком
(`fatal=True` по умолчанию):

```python
result = session.show_track_chain("bass")     # data["chain"] — список этапов
if len(result.data["chain"]) == 0:
    session.track_chain_add("bass", "arpeggiate step=0.25")  # строка-спецификация
session.track_chain_remove("bass", 1)         # индекс с единицы
```

Контракт данных для ветвления — только поля `EngineResult.data`:
`data["chain"]` — список этапов строками-спецификациями (формат понимает
обратный вызов `track_chain_add(name, spec)`), `data["stage"]` — спецификация
добавленного этапа; тексты сообщений контрактом не являются. Ошибка вызова
останавливает скрипт (`ScriptError`); строгий режим скрипт организует сам —
`fatal=False` + проверка `result.error`. На drum-дорожке `track_chain_add`
возвращает успех с предупреждением в отчёте — скрипт продолжается. Арность
вызовов проверяет `script check` до исполнения.

## Скрипты

Сессию можно поднять Python-скриптом — синхронный батч типизированных вызовов
(без музыкального времени и ожиданий; история версий `evolve`/`undo`/`recall` —
зона REPL, в скриптах нет). Скрипт — обычный `.py`-файл; импортов не нужно:
в его globals раннер инжектирует `session`, `TrackProposal`, `DrumProposal`.

Пример (см. `proposal_script.py` в корне):

```python
pad = TrackProposal(
    name="Track 1",
    profile_name="atmos",
    voicing="1-3-5-7",
    degrees=[6, 5, 4],   # ступени 0..13 (0-based, две октавы; тоника — [0])
)
session.add_track(pad)
session.add_drum(DrumProposal(name="Kick"))
session.set_bpm(120)
session.route_track("Track 1", "main")
session.start()
```

Проверка и исполнение:

```bash
uv run python -m src.main --repl
ars> script check proposal_script.py   # только валидация, без исполнения
ars> script run proposal_script.py     # исполнение с отчётом
```

Формат отчёта `script run`: заголовок `script <file>:`, затем фидбек движка
по каждому вызову (`NNN| <message>`), в конце `ok: N call(s)` или `error: ...`.
Диагностики валидатора выводятся как `file:line: message`; при наличии
диагностик исполнение не начинается. Ошибка вызова по умолчанию останавливает
скрипт (`ScriptError`); `fatal=False` возвращает `EngineResult` как есть —
скрипт сам решает, продолжать ли.

### Точки запуска

```bash
uv run python -m src.main --script setup.py      # разовый скрипт перед main loop
```

```yaml
scripting:
  # Стартовый скрипт: исполняется после сборки App, до main loop.
  startup: "setup.py"
```

Порядок: startup из config → `--script` из CLI. Семантика провалов —
**fail-fast**: если startup или `--script` провалился (валидация или ошибка
исполнения), приложение завершается до входа в main loop (`exit 1` с отчётом
в логе/консоли) — «устройство всегда включается» с кривым скриптом не стартует.
Откат применённых шагов не выполняется (транзакционность вне скоопа): уже
созданные дорожки остаются в сессии до рестарта.

## Drum-паттерны из REPL и скриптов

Ритм lane'а drum-дорожки задаётся строкой-нотацией — из REPL или скрипта.
Каждая дорожка — 16 lane'ов (GM 36–51), сетка 16 шагов (по умолчанию).

### Синтаксис нотации

| Элемент | Значение |
|---------|----------|
| `x` | удар, нормальная громкость |
| `X` | удар, акцент |
| `.` или `~` | пауза (два синонима) |
| пробел, `\|` | игнорируются — визуальная группировка (тактовая черта) |
| `(p,s)` | евклидов ритм на весь цикл паттерна: сетка делится на `s` равных сегментов, `p` из них активны (bjorklund), удар — на старте сегмента |
| `(p,s,offset)` | то же, сдвинутое на `offset` сегментов вправо (ролл до растягивания на сетку) |

Нотация — либо литеральные ячейки, либо ровно одна евклид-группа: смесь
литералов с евклидом — **ошибка**. Пустая нотация означает очистку lane'а.

### Длина относительно сетки

Нотация компилируется относительно текущей сетки дорожки (16 шагов):

- литеральные ячейки: короче сетки — дополняются паузами до конца такта,
  длиннее — **ошибка** (обрезки молча нет): `x.x.` на сетке 16 → удары
  в шагах 0 и 2, остальные молчат;
- евклид-группа всегда разворачивается на весь цикл паттерна (при сетке 16 —
  такт; при 32/64 — 2/4 такта); `s` больше числа
  шагов сетки — **ошибка** (например `(3,32)` на сетке 16); `p = 0` —
  все нули (легальная очистка), `p > s` — **ошибка**.

Примеры евклида на сетке 16: `(3,8)` — удары на шагах 0, 6, 12
(интервал 1.5 бита); `(8,8)` — восьмые 0, 2, …, 14, то есть `[1,0]×8`
(НЕ сплошная сетка — сплошная была бы `(16,16)`); `(4,4)` — четверти
0, 4, 8, 12; `(5,5)` — неравномерное деление 0, 3, 6, 9, 12;
`(3,8,1)` — сдвиг на один сегмент: удары 2, 8, 14.

### REPL

```
drum add [name]                          # создать drum-дорожку (без имени — автоимя)
drum pattern <track> <lane> [<notation>] # задать паттерн lane'а
```

Lane адресуется индексом `0..15`, GM-номером `36..51` или именем (без учёта
регистра): `kick`, `36` и `0` — один и тот же lane. Команда с двумя
аргументами (без нотации) очищает lane:

```
drum add
drum pattern "Drums" kick x..x|x..x|....|....
drum pattern Drums 38 ....X... ....X...
drum pattern Drums shaker (3,8)
drum pattern Drums conga (2,8,3)
drum pattern Drums kick        # очистить lane kick
```

Нотация может содержать пробелы и `|` без кавычек; имена дорожек с пробелами —
в кавычках. Автодополнение подсказывает действия `drum`, имена дорожек после
`drum pattern` и имена lane'ов следующим токеном.

### Скрипт

Тот же вызов доступен скриптам: `session.set_drum_pattern(name, lane, pattern)`.
Исполняемый пример — `examples/drum_dub.py` (создание drum-дорожки, бит
kick/snare/hat литералами, евклид на перкуссии, запуск транспорта):

```bash
uv run python -m src.main --repl
ars> script check examples/drum_dub.py
ars> script run examples/drum_dub.py
```

### История версий

Правка паттерна записывается в линейную историю версий дорожки как новая
версия — `undo`/`recall` работают после ручных правок так же, как после
шагов мутации (`evolve`). Повторная установка **того же** паттерна не
создаёт дубликат версии («без изменений»). Drum-дорожка, созданная из REPL
или скрипта, регистрируется в механизме истории в момент создания. При
`mutation.enabled=false` в конфиге паттерн применяется к звуку, но без
записи версии — в подтверждении будет note.

Оператор вероятности `?` и альтернатива `a|b` в нотации пока не поддержаны
(осознанное ограничение v1 — см. design.md §3 change'а
`add-drum-pattern-api`).

## Запись в MIDI-файл (capture)

Приложение умеет записывать свой MIDI-вывод в SMF-файл (`.mid`) с реальными
таймингами — для проверки бита без DAW. Записывается ровно то, что транспорт
доставил в порты: note_on/note_off всех дорожек, канал как есть (drum — 9).
CC-автоматизация, all-notes-off и real-time клок в файл не пишутся.

Команды REPL:

```
capture                       # статус: активен ли захват, путь, bpm, счётчик
capture start [path]          # начать запись (без пути — имя сгенерируется)
capture stop                  # остановить запись и создать файл
```

- Без аргумента файл создаётся как `captures/capture_YYYYmmdd_HHMMSS.mid`
  (каталог создаётся при необходимости); коллизия внутри той же секунды
  разрешается суффиксом `_NN`.
- Явный путь используется как указан; путь с пробелами — в кавычках или
  без (склеится): `capture start "My Takes/take 1.mid"`.
- **Перезапись запрещена**: старт с существующим путём даёт ошибку; если
  файл появился между стартом и стопом, стоп тоже даст ошибку, а не затрёт.
- Формат: SMF type 0, один трек, 480 тиков на бит (= разрешение таймлайна),
  меты track_name / set_tempo / time_signature 4/4. Tempo = BPM **на момент
  старта захвата** — смена BPM во время записи в файле не отражается.
- Позиции нот — реальные моменты доставки в битах от нуля таймлайна
  (для нот, отложенных свингом, — фактический момент слышимости), тактовая
  сетка сохраняется. note_off пишется настоящими note_off-событиями.
- Захват можно начать и при остановленном транспорте — после `start`
  доставленные события начнут накапливаться. Файл создаётся только на
  `capture stop`.

Приёмка файла — диагностическим спайком:

```bash
uv run python spikes/spike_midi_dump.py captures/capture_20261119_120000.mid --drum-dub
```

Спайк покажет структуру (SMF type, PPQ, tempo), аномалии (залипшие ноты,
off-grid позиции) и — с `--drum-dub` — разбор ударных по lane'ам эталона
`examples/drum_dub.py` (kick/snare/hat/shaker/conga: позиции на 16-й сетке,
канал 9, velocity-полосы).

Из скриптов доступны те же операции: `session.capture_start()` /
`session.capture_start("путь.mid")` / `session.capture_stop()`
(ошибка движка по умолчанию останавливает скрипт — `fatal=False` возвращает
результат как есть).
