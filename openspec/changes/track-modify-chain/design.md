# Design

## Context

Библиотека `src/session/modify/` готова (B1–B4): `Chain` — упорядоченный набор
frozen-этапов над списком событий, `ArpeggiateStage` разворачивает аккорды в
арпеджио, `DensifyStage` прореживает по позиции. Контракт протокола `Stage`:
этап получает весь список, возвращает новый, не знает соседей, не хранит
состояние между тиками. Но цепочка никуда не подключена: `Track` не хранит её,
`MelodicEngine` не применяет, REPL не управляет. Код стабилен: 1945 passed,
база линтеров удержана (ruff 50 / black 11 / mypy 20 — пре-существующие).

## Goals / Non-Goals

**Goals:**

- Подключить `Chain[NoteEvent]` к дорожкам: хранение в `Track`, источник —
  `MelodicProfile`, применение в `MelodicEngine`, управление из REPL.
- Дать скриптам (план G2) управление цепочкой: плоские 1:1 обёртки
  `ScriptSession` над фасадными методами со стабильным контрактом данных
  (`data["chain"]`/`data["stage"]`).
- Семантика «на лету» (вариант B из интервью): замена цепочки слышна со
  следующего тика, без квантизации на границу ступени.
- Починить известные дефекты modify/: приватный импорт `_density_keep`,
  усечение `int(e.beat)`, отсутствие валидации `density`, нетипизированные
  сигнатуры этапов, мутабельность `Chain`.
- Удержать слои: новый `src/session/model/density.py` — ниже modify/ и engine/.

**Non-Goals:**

- Новые этапы (Transpose, Drop): реестр этапов спроектирован расширяемым,
  но новых этапов в этой change нет.
- Цепочки для drum-дорожек: `DrumEngine` игнорирует непустую цепочку с
  предупреждением; дизайн — отдельная работа.
- REPL-команда `set` (полная замена): эмулируется последовательностью
  remove/add; отдельный метод фасада не добавляется.
- Статическая проверка литеральных спецификаций этапов в `ScriptValidator`
  (например «arpeggiate:step=0.25»): семантика спецификаций проверяется
  рантаймом через реестр этапов; валидатор проверяет только арность, новые
  методы `ScriptSession` подхватываются рефлексией `_facade_methods()`
  без правок validator.py.
- `ScriptRunner`/`_TracedSession`/`format_report` не меняются: обёртки
  подхватываются через `__getattr__`-обёртку подсчёта вызовов.
- Отображение цепочки в `track show`/StatusSnapshot: `track chain <name> show`
  покрывает потребность; трогать снапшот излишне.
- Смена механизма прореживания `track.density` (макро-ось DEN): остаётся в
  генераторах, цепочка — отдельный механизм.

## Decisions

### 1. Хранение: `Track.chain` — property в базовом ABC

- `Track.__init__` (`src/session/model/track.py`) инициализирует
  `self._chain: Chain[NoteEvent] = Chain()`; property `chain` с сеттером.
- Сеттер — fail-fast (инвариант «в треке всегда валидная цепочка»):
  - не `Chain` → `TypeError`;
  - элемент `stages` без `name` (str) или без callable `process` → `ValueError`.
  Параметры этапов валидируются самими этапами при конструировании (frozen
  dataclass `__post_init__`), поэтому сеттер проверяет только структуру —
  некорректный этап не может быть создан, а значит не может попасть в цепочку.
- Импорт `Chain` из `src.session.modify.chain` в `model/track.py` — допустимое
  направление: `modify/chain.py` — чистый листовой модуль (только stdlib),
  циклов не возникает (modify.densify импортирует model.density — листовой,
  см. §5). Модуль `chain.py` трактуется как типовой слой (аналог `midi/abc.py`).
- `set_profile` **не** сбрасывает `chain` (симметрично `degrees`/`density`/
  `sources`): цепочка — пользовательское состояние дорожки, а не свойство
  профиля после создания.

### 2. Источник цепочки: `MelodicProfile.chain` (frozen)

- `MelodicProfile` получает поле `chain: Chain[NoteEvent] = field(default_factory=Chain)`.
  `Chain` после фикса frozen, этапы frozen — копируется ссылка, безопасно.
- `MelodicTrack.__init__`: `self.chain = profile.chain` (через сеттер базового
  класса). Дальше REPL меняет только дорожку; профиль неизменен.
- Все профили реестра `PROFILES` (pad, atmos, sub, stab, seq, arp, bass, lead,
  texture, cc_filter, cc_space) получают **пустую** цепочку по умолчанию.
  Рассмотренные кандидаты и отказ:
  - `arp` — генератор-слайсер shape="arp" **уже** раскладывает аккорд по
    ступеням; `ArpeggiateStage` поверх не нашёл бы групп (ноты не совпадают по
    beat) — осмысленного поведения нет, а различие профилей было бы ложным;
  - `pad`/`atmos` — арпеджио блок-аккорда музыкально осмысленно (классика
    dub techno), но непустой дефолт менял бы звучание существующих сессий и
    удваивал бы пользовательский путь («хочу арпеджио» — одно действие из
    REPL и так);
  - `bass`/`lead`/`texture` — генератор уже прореживает по макро-оси DEN
    (`track.density`); дефолтный `DensifyStage` дал бы двойное прореживание;
  - `sub`/`stab`/`seq` — рисунок задаётся евклидом/формой слайсера; цепочка
    с дефолтом не добавляет смысла.
  Итог: цепочка — opt-in механизм на дорожке; дефолт всех профилей —
  тождественная пустая цепочка. Тест фиксирует: у каждого профиля в
  `PROFILES` `len(chain) == 0` (и у новых профилей тоже, через проверку
  реестра, а не перечисления имён).

### 3. Точка применения: `MelodicEngine._pattern()`, единообразно для всех семей

- `MelodicEngine._pattern()` после `generate_notes(ctx)` применяет
  `self._track.chain.process(notes, stage_ctx)` к списку `NoteEvent` паттерна.
  Пустая цепочка — тождество (`Chain.process` возвращает копию входа) —
  текущее поведение движка не меняется ни на один бит.
- Применение **единообразно для всех семей** (chord_source, free_mono,
  chord_slicer): все они порождают `NoteEvent` — именно их ждут этапы
  (поля `beat`/`degree`/`duration`/`velocity`). Бриф упоминал «free/stab/seq»;
  трактовка: «паттернный outbox генератора» — это весь список `NoteEvent` от
  `generate_notes`, ограничение по семьям внесло бы произвольное различие
  (pad-аккорд нельзя было бы арпеджиировать — главный пользовательский
  сценарий). Chord outbox (`ChordEvent` в `track.outbox`) и копии
  `inject_sources` **не трогаются** — они питают граф гармонии
  (`propagate_chords`) и окно слайсеров; chord-события сломали бы
  гармонический граф (бриф, п. 3).
- Цепочка применяется к **относительным** beats одного цикла паттерна;
  циклическое повторение и резолв ступеней в MIDI — забота планировщика, как
  раньше. `pattern_length_for(ctx)` не зависит от цепочки (период слайсеров —
  цикл аккордов окна, остальных — спецификация профиля).
- `StageContext`: движок строит `StageContext(beat=self._origin,
  track_name=self._track.name)`. `bpm` не подключён (движок не читает клок):
  полю `StageContext.bpm` даётся дефолт `0.0` с пометкой «темп не подключён;
  этапы не используют» — аддитивное изменение frozen dataclass, существующие
  вызовы `StageContext(beat, bpm, track_name)` продолжают работать. Если
  будущему этапу понадобится темп — подключается отдельной change (атрибут
  движка, прокинутый из приложения).

### 4. Семантика «на лету» (вариант B): замена — со следующего тика

- `MelodicEngine` хранит `self._chain_seen: Chain[NoteEvent] | None = None`.
  В `tick()`, после `ensure`/обработки pending-прогрессии и перед
  `_extend_horizon`, движок сравнивает по **идентичности** (`is`):
  `track.chain is not self._chain_seen` → горизонт пересобирается с новой
  цепочкой:
  - `cancel_from(now)` — снимаются запланированные вперёд note-on старой
    цепочки (note-off не трогаются — звучащие ноты доигрывают, тот же
    механизм, что у отложенной прогрессии B2);
  - `rewind_to(now)` — если watermark > now, знак возвращается на текущий бит;
  - `_chain_seen = track.chain`.
  Пересборка горизонта происходит естественно в `_extend_horizon` на этом же
  тике — изменения слышны со следующего тика, без ожидания границы ступени.
  Идентичность вместо `==`: REPL создаёт новый `Chain` на каждую правку,
  сравнение `is` дёшево и однозначно; frozen `Chain` делает `==` тоже корректным,
  но `is` проще и исключает ложные срабатывания при совпадении содержимого.
- Взаимодействие с pending-прогрессией (B2): если в одном тике и та, и другая
  правки — сначала применяется отложенная прогрессия (граница ступени), затем
  пересборка цепочки от `now`; `_extend_horizon` режет окно по границе ступени
  внутри окна, так что обе правки применяются корректно в одной сборке.
- `revision` **не трогается**: он про degrees/voicing/inversion/profile;
  производные (NoteDrift, кэши) на цепочку не реагируют.
- Первый тик: `_chain_seen is None` → «замена» обнаруживается сразу, но
  `cancel_from` на пустом планировщике — no-op; поведение не меняется.
- Если `port_label is None` (дорожка молчит), ранний return стоит до проверки
  цепочки — ничего не запланировано, цепочка подхватится при подключении порта
  (stale `_chain_seen` гарантирует обнаружение).

### 5. Фикс слоёв: `src/session/model/density.py`

- Новый модуль `src/session/model/density.py`: публичная функция
  `density_keep(index: int, density: float) -> bool` (бывшая
  `generators._density_keep`, тело без изменений — детерминированный фильтр
  D2 §3.6). Модуль — листовой (только stdlib), ниже modify/ и engine/:
  `generators.py` и `modify/densify.py` импортируют оттуда, циклов нет.
- Приватный кросс-модульный импорт `_density_keep` устранён; имя
  `_density_keep` исчезает из публичного пространства (переименование
  фиксируется тестом: импорт из `engine.generators` больше не существует).
- Обновляемые тесты: `tests/test_modify_densify.py` импортирует
  `density_keep` из `model.density`; тест-инспекция исходника генератора
  (`test_generator_already_thins_by_density`) обновляет искомую строку на
  `density_keep(i, track.density)` и получает обновлённый docstring —
  прореживание макро-оси DEN остаётся в генераторе, `DensifyStage` в цепочке —
  отдельный механизм (двойного прореживания у дефолтных профилей нет, т.к.
  дефолтные цепочки пустые, §2).

### 6. Контракт Densify и валидация

- Docstring `DensifyStage`: контракт **«Densify — до этапов, дробящих время»**
  (арпеджиатор, будущие транспозиции времени). Решение по `int(e.beat)` осмысленно
  только на сетке целых битов: после `ArpeggiateStage` все ноты получают
  дробные биты внутри целого такта и схлопываются в один индекс — решение
  деградирует. Это **документированное поведение**, а не баг: этап не запрещает
  такой порядок, но контракт требует ставить Densify раньше.
- Тест на документированное поведение: цепочка `[Arpeggiate, Densify]` на
  аккорде — арпеджио разворачивается, Densify применяет решение по
  «схлопнутым» индексам (все ноты первого такта → index 0 → сохраняются
  как акцент); фиксированный snapshot-тест фиксирует результат, чтобы
  изменение семантики не произошло молча.
- `DensifyStage.__post_init__`: валидация `0.0 <= density <= 1.0`, иначе
  `ValueError` (по образцу `ArpeggiateStage.__post_init__`).
- Типизация этапов: `process(self, batch: list[NoteEvent], ctx: StageContext)
  -> list[NoteEvent]` — сигнатуры `Stage[NoteEvent]`-совместимы. Существующие
  тесты с duck-typed событиями (`Ev`, `N`) продолжают работать (аннотации
  не проверяются в рантайме; mypy гоняется только по `src`).

### 7. `Chain` — frozen dataclass

- `@dataclass(frozen=True)` для `Chain[T]`; `stages: Sequence[Stage[T]] =
  field(default_factory=tuple)`. Пустая цепочка — тождество, `process`/
  `names`/`__len__` без изменений. Frozen делает цепочку безопасной для
  совместного использования между профилем и дорожками (§2) и для
  snapshot-сравнения по идентичности (§4).
- Тестовый fake `Drop` в `tests/test_modify_densify.py` — обычный класс, не
  dataclass: на frozen `Chain` не влияет.

### 8. Фасад и REPL

- **Реестр этапов** — новый модуль `src/session/modify/stage_registry.py`:
  `STAGE_FACTORIES: dict[str, Callable[[Mapping[str, str]], Stage[NoteEvent]]]`
  (`arpeggiate`, `densify`), `build_stage(name, params) -> Stage[NoteEvent]`
  (неизвестное имя/параметр/плохое значение → `ValueError` с русским
  сообщением; `densify` требует явный `density` — скрытых дефолтов нет),
  `format_stage(stage) -> str` (`arpeggiate step=0.25 direction=up`) для
  показа. Слой modify, импортов вверх нет; добавление нового этапа — одна
  строка в реестре.
- **Методы фасада** (`src/repl/engine_control.py`, не абстрактные, дефолт
  `EngineResult.fail("... not supported by this control")` — прецедент C1–C4):
  - `track_chain(name: str) -> EngineResult` — показать цепочку
    (`track "Pad 1": chain = arpeggiate step=0.25 direction=up` или
    `chain = — (empty)`);
  - `track_chain_add(name: str, stage_name: str,
    params: Mapping[str, str]) -> EngineResult` — добавить этап в конец,
    вернуть новую цепочку;
  - `track_chain_remove(name: str, index: int) -> EngineResult` — удалить
    этап по **1-based** индексу (REPL-нумерация для человека, как в
    показе), вернуть новую цепочку; вне 1..len — ошибка.
- **Реализация** (`src/app/engine_control.py`): через `_melodic_track(name)`
  (ошибка «not found» — как у set_track_gate). **Drum-дорожки** (§11,
  решение ревизии): все три операции возвращают успешный результат с явным
  текстом-предупреждением — спецификация не применяется, `track.chain` не
  изменяется (`DrumEngine` цепочку игнорирует). Единое поведение фасада
  для REPL и скриптов: обёртка 1:1 не может «погасить» ошибку фасада,
  значит семантика обязана жить в фасаде. Предупреждение движка (§3.5,
  задача 3.5) остаётся защитой для прямого присвоения цепочки в модели —
  через фасад drum-дорожка непустую цепочку не получит.
- **REPL**: `CommandSpec` `track chain <name> show | add <stage> [k=v ...] |
  remove <n>` (`min_args=2, max_args=16, join_args=False`; имена дорожек с
  пробелами — в кавычках, как у `track sources`). Executor `_cmd_track_chain`:
  действие — второй токен; параметры `add` — пары `k=v` (дубликат ключа или
  отсутствие `=` — ошибка), значения передаются строками в `build_stage`
  (конверсия — забота реестра). Ошибки — `CommandResult(code=1)`, цикл живёт.
- **Автодополнение**: после `track chain` — имена дорожек (динамический
  контекст, как `track delete`), действия `show|add|remove` — из статического
  дерева, после `add` — имена этапов через провайдер `"stage"` (инжект из
  `main.py` из `STAGE_FACTORIES` — то же расслоение, что у провайдеров
  `"profile"`/`"lane"`: `repl/` не импортирует `session`).

### 9. Щелчок на стыке арпеджио и следующего аккорда — дизайн-заметка (вне скоупа)

Замечание из ревью: последняя нота арпеджио заканчивается ровно на onset
следующего аккорда (`_fit_step` кладёт `gap / count` шагов до границы) —
потенциальный глухой off/on в один бит. Разбор: off и on приходятся на
**разные** MIDI-ноты (ноты арпеджио не повторяются по кругу: `up`/`down` —
строго по ступеням, `updown` — крайние не повторяются), а коллизия одного
питча в один бит безопасна на уровне синтезатора (перезапуск голоса) —
глухого щелчка нет. Укорачивание на эпсилон усложнило бы математику
`_fit_step` ради несуществующей проблемы. **Зафиксировано как дизайн-заметка;
в скоуп не входит.** Если на железе появится артефакт — отдельная change с
эпсилон-укорочением последней ноты.

### 10. Конфиг-связка

Не требуется: профили и их дефолтные цепочки — код (`PROFILES`), конфиг
(`config.yaml`) никаких chain-настроек не получает. REPL меняет цепочку
рантайм-only; сохранение пользовательских цепочек между запусками — вне скоупа
(как и прочие рантайм-правки дорожек).

### 11. Скриптовый фасад: `ScriptSession` (решение ревизии)

Решение ревизии: скриптовые модификации трека через chain **входят** в этот
change (ранее — follow-up). `ScriptSession` — плоские 1:1 обёртки над
фасадными методами в стиле `set_track_gate`/`set_drum_pattern` (через
`_call`, `fatal=True` по умолчанию):

- `show_track_chain(name)` → фасадный `track_chain(name)`. Контракт данных:
  `data["chain"]` — список этапов-строк-спецификаций (`format_stage`,
  например `"arpeggiate step=0.25 direction=up"`), пустая цепочка — пустой
  список. Скрипт ветвится по содержимому
  (`if len(result.data["chain"]) == 0: ...`).
- `track_chain_add(name, spec)` — строка-спецификация
  `"arpeggiate step=0.25 direction=up"`; обёртка парсит её функцией
  `parse_stage_spec(spec)` из реестра этапов (`ValueError` → при
  `fatal=True` `ScriptError`, иначе `EngineResult.fail`) и вызывает
  фасадный `track_chain_add(name, stage_name, params)`. Контракт данных:
  `data["stage"]` — спецификация добавленного этапа, `data["chain"]` —
  итоговая цепочка.
- `track_chain_remove(name, index)` → фасадный `track_chain_remove(name,
  index)` 1:1. Контракт данных: `data["chain"]` — итоговая цепочка.

- **Формат данных — строки-спецификации, а не структуры**: `format_stage` —
  канонический текст реестра, обратно совместим с `track_chain_add(name,
  spec)` (круговая согласованность `parse_stage_spec(format_stage(s))` —
  тест); отдельное JSON-подобное представление параметров не нужно.
- **Стабильный контракт для скриптов** (решение ревизии): только поля
  `EngineResult.data` (`data["chain"]`, `data["stage"]`); тексты
  `EngineResult.message` — свободные, не контракт.
- **Drum-дорожки — не fail-fast** (решение ревизии): `track_chain_add` на
  drum-дорожке возвращает успешный `EngineResult` (error=False) с текстом-
  предупреждением — спецификация не применяется, скрипт продолжает работу,
  предупреждение попадает в `output_lines` отчёта (`_TracedSession.__getattr__`
  собирает `result.message`) и в лог. Строгий режим скрипт организует сам
  через fatal-механику (`fatal=False` + проверка `result.error`).
- **`ScriptValidator` НЕ трогается**: `_facade_methods()` строит таблицу
  методов рефлексией `inspect.signature(ScriptSession)` — новые методы
  автоматически попадают в линт арности (вызов с неверным числом аргументов
  диагностируется до исполнения). Семантика спецификаций этапов проверяется
  рантаймом через `parse_stage_spec`/`build_stage`; статическую проверку
  литеральных спецификаций не добавляем.
- **`ScriptRunner`/`_TracedSession`/`format_report` НЕ меняются**: обёртки
  подхватываются автоматически через `__getattr__`.
- Импорт `src.session.modify.stage_registry` в `src/scripting/script_session.py`
  — новое ребро `scripting → session.modify` (в рамках документированного
  исключения «scripting тянется вверх к session»); циклов нет
  (`stage_registry` — листовой модуль слоя modify). Отразить в AGENTS.md
  (задача 7.2).

## Risks / Trade-offs

- [Пересборка горизонта при замене цепочки] → тот же механизм, что у
  отложенной прогрессии (B2): cancel_from + rewind проверены тестами;
  стоимость пересборки одного окна — как обычный тик достройки горизонта.
- [Двойное прореживание DEN + Densify] → у дефолтных профилей цепочки пустые
  (§2); пользователь, добавивший `DensifyStage` к free_mono-дорожке, осознанно
  комбинирует два механизма — поведение документировано в README.
- [Frozen `Chain` ломает существующий код, мутирующий stages] → такого кода
  нет (grep по `chain.stages`/`Chain(` в src/): цепочка до сих пор не
  подключена; тесты конструируют через конструктор.
- [Импорт `model.track` → `modify.chain` и `modify.densify` → `model.density`]
  → направленные рёбра без циклов: `modify.chain` и `model.density` — листовые
  модули. Проверяется тестом-инспекцией (import graph) или отсутствием
  ImportError при запуске тестов.
- [Дрейф спек от кода] → дельты формулируют внешне наблюдаемое поведение
  (команды, сообщения, инварианты); имена классов — только в design/tasks.
- [Предупреждение вместо отклонения для drum-дорожек] → пользователь может
  не заметить, что спецификация не применена; текст предупреждения — явная
  часть сообщения, README фиксирует поведение, скриптовый отчёт содержит
  предупреждение.
- [Дрейф скриптового контракта данных] → контракт — только поля
  `data["chain"]`/`data["stage"]` (строки-спецификации, круговая
  согласованность с реестром — тестом); тексты сообщений контрактом не
  являются и меняются свободно.

## Migration Plan

Обычный код-change поверх baseline: реализация по tasks.md снизу вверх
(фиксы modify/ → модель → движок → фасад → скрипты → REPL → README),
регрессия — полный прогон 1945 тестов + новые блоки. Данных/конфигов для
миграции нет: у всех профилей дефолтная пустая цепочка, поведение сессий
не меняется.
