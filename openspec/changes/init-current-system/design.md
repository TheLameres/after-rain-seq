# Design

## Context

Проект — генеративный MIDI-хост (см. proposal.md — Why). Код стабилен:
1830 passed тестов, база линтеров удержана. Описание поведения сейчас
размазано по `AGENTS.md`, `docs/track-hierarchy.md`,
`docs/mutation-manual-spec.md`, `plans/ROADMAP.md` и `README.md`; в
`openspec/specs/` пусто. Доки остаются источником контекста, но
машиночитаемого контракта поведения нет.

## Goals / Non-Goals

**Goals:**

- Создать baseline из 8 capability-спек, описывающих **текущее** реализованное
  поведение (то, что проверено тестами и прогонами).
- Зафиксировать в требованиях внешне наблюдаемое поведение (REPL-команды,
  кнопки Push 2, статусы портов, лимиты), а не внутренние имена классов.
- После archive: `openspec/specs/` становится отправной точкой для дельт
  будущих изменений (D3, E1/E2, хвост C2).

**Non-Goals:**

- Не описывать нереализованное: D3 (режимы падов), хвост E1 (персист клока/
  портов в конфиг), E2 (systemd, 8-часовой прогон), хвост C2 (валидация пары
  лад+войсинг).
- Не фиксировать известный техдолг как требования (см. Decisions).
- Не менять код, конфиги и доки проекта.

## Decisions

- **Гранулярность — 8 capabilities по подсистемам** (harmony, track-graph,
  drum-engine, mutation, clock-sync, midi-routing, push2-ui, repl-control).
  Альтернатива — одна большая спека: отвергнута, дельты по точечным
  изменениям будут неудобны. Границы совпадают со слоями из `AGENTS.md`,
  поэтому каждая будущая change обычно затрагивает 1–2 спеки.
- **Только реализованное поведение.** Техдолг сознательно не включён в
  требования: двойное применение свинга, on-demand melodic-дорожки вне
  MutationEngine (играют базовый материал), Transport Mode B (EXTERNAL —
  интерфейс заложен), отложенное мигание дисплея TRACKS/VERSIONS (сейчас
  текстовый флаг), ручной прогон UI на железе, LCXL3 DAW CC→DIN не проверен.
  Когда техдолг закроется, это будет дельта `MODIFIED`/`ADDED` к соответствующей
  спеке. Альтернатива — включить нереализованное: отвергнута, спека перестала
  бы сходиться с реальностью.
- **Источники контента:** `docs/mutation-manual-spec.md` (статус «реализовано»,
  решения в шапке), `docs/track-hierarchy.md`, сводка и разделы планов
  B1–B4/C1–C6/D1–D2/F1 из `plans/ROADMAP.md`, `README.md` (конфиг, порты,
  REPL). Факты сверены с кодом там, где доки противоречили: маппинг
  энкодеров взят из `src/devices/push2/mapping.py` (track 1–8 = CC 71–78,
  master = CC 79 — строка «CC 78 = master» в `AGENTS.md` устарела).
- **Язык требований — русский.** Проектная конвенция (AGENTS.md: бизнес-логика
  — русский); структурные ключи формата (`## ADDED Requirements`,
  `#### Scenario:`, WHEN/THEN) остаются на английском — их требует валидатор.
- **Терминология без имён классов.** В требованиях — «дорожка-источник»,
  «сетка версий», «логический лейбл», «фасад контроля». Имена модулей упоминаются
  только в design/tasks, не в спеках: реализация может меняться без смены
  поведения.

## Risks / Trade-offs

- [Дрейф спек от кода] → новые изменения всегда идут как changes с дельтами;
  при изменении поведения обновлять спеку в той же change.
- [Спеки шире кода в мелочах] → каждая спека ограничена внешне наблюдаемым
  поведением и лимитами, проверенными тестами; при archive прогонять
  `openspec validate --strict`.
- [Дублирование с доками] → доки остаются «почему и как», спеки — «что
  наблюдается»; в спеках нет ссылок на планы, дублирования деталей — минимум.

## Migration Plan

1. Дельты этого change валидируются (`openspec validate init-current-system`).
2. После ревью — sync/archive: дельты переносятся в `openspec/specs/<capability>/spec.md`
   (8 новых спек).
3. Откат тривиален: до sync/archive достаточно удалить change-каталог;
   после — восстановить из git.

## Open Questions

Нет: все спорные места (гранулярность, включение техдолга, язык) решены
с пользователем до создания артефактов.
