# Design

## Context

Доставка MIDI уже сосредоточена в одном месте: `Transport.process_events()`
(`src/sync/transport.py`) разбирает очередь `CaptureOutput` → `TransportEvent`,
применяет свинг (`_schedule` откладывает NOTE_ON, `_release_due` выпускает
дозревшие) и в `_deliver` шлёт в порт через `PortRegistry`. Рядом уже живёт
диагностический буфер `MidiTrace` (`src/sync/midi_trace.py`) — записывает
в `_deliver` и реально отправленное, и отброшенное (deque под GIL, пишет
поток TickProxy, читает REPL). Событие несёт `beat` — позицию генерации
на таймлайне; свинг сдвигает onset на `event.beat + delay`. Текущее время
таймлайна приходит в `process_events(current_beat=...)` из хука
`hooked_dispatch` (`src/app/application.py`). BPM доступен в хуке как
`cm.state.bpm or self._sync_bpm`. mido в зависимостях, но в `src/` пока
не используется для записи SMF — `spikes/spike_midi_dump.py` только читает.

Мотивация — верификация бита без DAW после инцидента с «ковром» 98k событий
в Live: нужен файл с реальными таймингами, который существующий спайк умеет
разбирать (структура, аномалии, `--drum-dub` по эталону `examples/drum_dub.py`).

## Goals / Non-Goals

**Goals:**

- Записать только то, что реально ушло в порты: note_on/note_off всех
  дорожек, канал как есть (drum → ch9), с реальной позицией в битах.
- Управление из REPL и скриптов через единственный фасад `EngineControl`;
  файл пишется на `capture stop`, без блокировок транспортного потока.
- Файл читается mido/спайком: PPQ 480, tempo-мета, один трек, note_off
  настоящими событиями 0x80.
- Перезапись существующего файла запрещена (ошибка, не деструктив).

**Non-Goals:**

- CC/автоматизация, ALL_NOTES_OFF, real-time клок в SMF — расширения будущего.
- Смена BPM во время захвата (один set_tempo на тик 0; треки с быстрыми
  сменами темпа — будущность).
- Секция `capture` в config.yaml — каталог по умолчанию константой.
- Push 2 UI для захвата.
- Починка clock self-echo — открытый баг в `plans/ROADMAP.md`, отдельный change.

## Decisions

### 1. Точка захвата: `_deliver`, рядом с trace, только доставленные

- Capture встаёт в `Transport._deliver` **после** успешного резолва порта
  (та же точка, где trace записывает `delivered=True`): в файл попадает ровно
  то, что услышал синтезатор. Отброшенные (порта нет) не пишутся — в отличие
  от trace, который их помечает; capture-to-SMF — запись вывода, а не диагностика.
- **Эффективный бит**: `event.beat` — позиция генерации, до свинга. Свинг
  сдвигает onset в будущее, и реальный момент слышимости — `deliver_at`
  из `_schedule`. Для SMF «реальные тайминги» — это слышимый момент:
  `_deliver` получает третий параметр `capture_beat`:
  - немедленная доставка из `_schedule` → `event.beat`;
  - выпуск из `_release_due` → сохранённый `deliver_at` (первый элемент
    кортежа `_held`).
  Позиции на 16-й сетке при этом не искажаются: свинг по конвенции проекта
  двигает onset в пределах шага (спека clock-sync: «позиция в сетке не
  меняется»), округление до тика PPQ 480 (30 тиков на 16-й шаг) сохраняет
  сетку с точностью ±1 тик.
- Фильтр по виду события — в точке вызова: capture пишется только для
  `NOTE_ON`/`NOTE_OFF`; `CONTROL_CHANGE` и `ALL_NOTES_OFF` мимо (состав v1).
- Альтернатива «снимать с trace-буфера» отвергнута: `MidiTrace` — кольцевой
  буфер `capacity=500`, старые события вытесняются — длинный захват терял бы
  данные. Альтернатива «второй isobar OutputDevice рядом с CaptureOutput»
  отвергнута: это позиция *генерации*, до свинга и до решения о доставке —
  не «как доставляет Transport».

### 2. Потокобезопасность: накопитель + запись на stop, атомарная замена ссылки

- События доставляет worker-поток TickProxy; `capture start/stop` идёт из
  REPL-потока. Кросс-поточное взаимодействие — без locks на горячем пути,
  по прецеденту `MidiTrace`:
  - `CaptureRecorder` накапливает записи в `list` — `list.append` атомарен
    под GIL, как `deque.append` в trace;
  - Transport держит ссылку `self._capture_sink`; старт/стоп — атомарная
    замена ссылки (`set_capture_sink(recorder | None)`); горячий путь —
    одна проверка `if sink is not None` + один append, без блокировок;
  - на `capture stop` фасад снимает sink, забирает снимок списка
    (`recorder.entries()` → новый список) и пишет файл в REPL-потоке.
- Гонки нет по построению: после снятия ссылки новые события не пишутся;
  снимок списка — неизменяемая копия на момент stop. Потеря хвоста из
  событий, доставляемых прямо в момент stop, ограничена и приемлема
  (музыкально — обрез последних миллисекунд), дубли исключены.
- Старт при остановленном транспорте — **разрешён**: sink прикреплён, события
  просто не доставляются (писать нечего); после `start` файл наполняется.
  Это отвечает критерию брифа «валидное поведение»: захват — свойство
  фасада, не транспорта.

### 3. Писатель: `SmfWriter` в `src/sync/smf_writer.py`, SMF type 0, PPQ 480

- Класс `SmfWriter` (один класс — один файл), метод
  `write(path: Path, entries: Sequence[CaptureEntry], bpm: float,
  ticks_per_beat: int = 480) -> None`. Слой `sync` — ниже `app`, импортирует
  только `capture_recorder` и mido; вверх не тянет ничего.
- Формат: `mido.MidiFile(type=0, ticks_per_beat=480)`, один трек:
  `track_name` ("after-rain-seq capture"), `set_tempo` (BPM на момент
  старта захвата, `mido.bpm2tempo`), `time_signature` 4/4, затем
  note-события. Type 0 выбран осознанно: один трек по брифу, максимальная
  совместимость с DAW-импортом и спайком (он обходит все треки, но меты
  читает по трекам — в type 0 они в единственном треке).
- **Тики**: абсолютный тик события = `round(capture_beat * 480)` от нуля
  таймлайна (не от момента старта захвата) — тактовая сетка сохраняется
  (бар 2 = биты 4–8), спайк считает `steps % 16` независимо от выравнивания
  файла. Дельты: события сортируются по составному ключу — первичный ключ
  абсолютный тик, вторичный — вид события (`note_off` = 0 раньше `note_on`
  = 1; при равных тике и виде сохраняется порядок доставки). Дельта первого
  = его тик, последующих — разность (отрицательных нет по построению
  сортировки).
- **Tie-break off-раньше-on — системная коллизия, а не экзотика**: гейт
  drum-удара `DEFAULT_GATE = 0.25` бита = ровно 1/16, поэтому note_off
  удара `k` попадает на тот же тик, что note_on удара `k+1` (соседние
  16-е одной lane, `(16,16)`, four-on-the-floor). Порядок доставки в
  транспортном потоке на этом не гарантируется: если note_on записать
  раньше note_off той же ноты, в файле возникает перекрытие одинаковых
  нот (DAW трактует как ретриггер либо залипание) — ровно тот класс
  артефактов, ради которых затевался capture. Вторичный ключ сортировки
  устраняет это детерминированно: на одном тике off всегда раньше on,
  независимо от порядка доставки. Для двух note_on разных нот на одном
  тике порядок не важен (разные питчи не перекрываются).
- note_off пишется настоящим `note_off` (0x80) — как доставляет Transport;
  спайк трактует и vel-0 note_on как off, совместимо в обе стороны.
- Перезапись запрещена технически: файл открывается `open(path, "xb")` —
  эксклюзивное создание; `FileExistsError` → ошибка движка. mido
  `MidiFile.save(file_object)` принимает открытый файл.
- Ошибки записи/пути (`OSError`) поднимаются из writer и превращаются
  фасадом в `EngineResult.fail` — REPL не падает.

### 4. Накопитель: `CaptureRecorder` в `src/sync/capture_recorder.py`

- Класс `CaptureRecorder`: `record(kind, channel, note, velocity, beat)`
  (вызывается Transport только для note-событий), `entries() -> list[CaptureEntry]`
  (копия-снимок), `__len__`. DTO `CaptureEntry` — frozen dataclass
  (`kind: EventKind`, `channel: int`, `note: int`, `velocity: int`,
  `beat: float`) в том же модуле (исключение «связанные DTO» из AGENTS.md;
  velocity для note_off — `None` → writer пишет 0? нет: note_off пишется
  как `note_off`-сообщение без velocity; поле хранит `None` и writer
  мапит). Никакого mido в recorder — writer отделяет накопление от формата.
- Ограничение объёма: файл растёт только в памяти между start и stop;
  защитный лимит не вводим (запись нормальной сессии — сотни–тысячи
  событий; runaway-поток — тот самый отдельный баг клока, и capture скорее
  инструмент его диагностики). Риск зафиксирован в Risks.

### 5. Tempo-мета: BPM на момент старта захвата

- Источник BPM — тот же, что в `hooked_dispatch`: `clock_manager.state.bpm`
  (может быть `None` при ожидании MIDI-клока) с fallback на `_sync_bpm`.
  Протокол `AppPorts` пополняется членом `sync_bpm: float` (read-only
  свойство App) — иначе фасаду неоткуда взять fallback; `clock_manager`
  в протоколе уже есть.
- BPM фиксируется в момент `capture_start` (вместе с путём) и пишется
  одним `set_tempo` на тик 0. Смена BPM посреди захвата в файле не
  отражается (Non-Goal) — документируется в README.
- Синхронизация с ритмом файла: PPQ 480 совпадает с `ticks_per_beat`
  Timeline — пересчёт beat→тик взаимно-однозначный.

### 6. Фасад: имена, состояние, автогенерация, ошибки

- Методы `EngineControl` (не абстрактные, дефолт `fail("capture is not
  supported by this control")`, прецедент C1–C4/`set_drum_pattern`):
  - `capture_start(path: str | None) -> EngineResult`;
  - `capture_stop() -> EngineResult`;
  - `capture_status() -> EngineResult`.
- Состояние захвата (recorder, путь, bpm) живёт в `AppEngineControl`
  (`self._capture_recorder/_capture_path/_capture_bpm`) — фасад
  однопоточный со стороны вызовов (REPL-поток/ScriptRunner).
- `capture_start`:
  1. транспорт недоступен (`sync.enabled=false`) → fail;
  2. захват уже активен → fail («capture already running — stop it first»);
  3. путь `None` → автогенерация `captures/capture_YYYYmmdd_HHMMSS.mid`
     (локальное время), каталог создаётся `mkdir(parents=True, exist_ok=True)`;
     коллизия внутри той же секунды → суффикс `_01.._99` (автогенерация —
     не «перезапись», а выбор свободного имени; явный путь такого не умеет);
  4. явный путь существует → fail сразу (ранний фидбек);
  5. BPM фиксируется, recorder создаётся и прикрепляется транспорту.
  Успех: «capture started → <path> (bpm X)» + data `{"path": ...}`.
- `capture_stop`: не активен → fail; sink снимается, снимок →
  `SmfWriter.write` (FileExistsError/OSError → fail, транспортный поток
  к этому моменту уже от sink отвязан); успех: «capture stopped:
  <path> (N note events)» + data.
- `capture_status`: активен → путь, счётчик событий, bpm; не активен →
  «capture is not active» (ok, не ошибка — это легальный ответ на `capture`).

### 7. REPL: домен `capture`

- Три `CommandSpec`:
  - `capture` (bare, `max_args=0`) — статус;
  - `capture start [path]` (`min_args=0, max_args=16, join_args=True` —
    путь с пробелами склеивается, конвенция `track delete`);
  - `capture stop` (`min_args=0, max_args=0`).
  Разбор по образцу домена `clock`/`drum`: bare + действия.
- Executor: `_cmd_capture` → `capture_status()`, `_cmd_capture_start` →
  `capture_start(args[0] if args else None)`, `_cmd_capture_stop` →
  `capture_stop()`; результат через `_feedback`. Не деструктивные
  (файл не перезаписывается — подтверждение не нужно).
- Автодополнение: статическое дерево дополняется само из таблицы
  `CommandSpec` (домен `capture`, действия `start`/`stop`); динамические
  провайдеры не нужны — пути не дополняем. `src/main.py` не трогается.

### 8. Скриптовый фасад и валидатор

- `ScriptSession.capture_start(path: str | None = None, *, fatal: bool = True)`
  и `capture_stop(*, fatal: bool = True)` — обёртки 1:1 через `_call`.
- `ScriptValidator._facade_methods` правок не требует: таблица строится
  рефлексией `inspect.getmembers(ScriptSession)` — новые публичные методы
  попадают в линт автоматически (подтверждено change'ом add-drum-pattern-api);
  факт фиксируется тестом: `script check` пропускает вызов с верной арностью
  и ловит неверную.

### 9. Слои и правила

- Новые модули — в `src/sync/` (ниже `app`): `app/engine_control.py`
  импортирует `capture_recorder`/`smf_writer`; циклов нет. `Transport`
  получает только вызов `sink.record(...)` — без знания о SMF/mido.
- Правило «кросс-поточное — через очереди/иммутабельные снимки» соблюдено:
  атомарная замена ссылки + неизменяемый снимок списка (решение 2),
  никаких разделяемых мутабельных структур.

## Risks / Trade-offs

- [Runaway-поток зальёт память] → без лимита накопителя (решение 4);
  риск тот же класс, что сам баг self-echo, и capture — инструмент его
  диагностики; если понадобится — стоп-по-лимиту отдельной change.
- [Свинг-сдвиг > шага сломал бы сортировку] → по конвенции свинг двигает
  onset в пределах 16-го шага; отрицательных дельт после сортировки нет
  в любом случае (сортировка стабильная). Порядок off/on на одном тике
  зафиксирован вторичным ключом (решение 3, tie-break off-раньше-on);
  остающийся худший случай — перескок порядка двух note_on разных нот на
  одном тике (разные питчи не перекрываются — безвредно).
- [Висячие note_on при stop посреди ноты] → файл честен: note_off не
  доставлен — его нет в файле; спайк пометит «залипшие» в аномалиях.
  Принимаем ( capture — снимок потока, не компоновка).
- [Расширение ABC ломает заглушкам контракт] → методы не абстрактные
  с дефолтом fail — существующие моки/стабы работают (прецедент).
- [Дрейф спек от кода] → дельты формулируют внешне наблюдаемое поведение
  (команды, файлы, ошибки); имена классов — только в design/tasks.

## Migration Plan

Обычный код-change: реализация по tasks.md снизу вверх (recorder → writer →
Transport sink → фасад → REPL → скрипты → README), регрессия и линтеры —
на исполнителе (в этом конвейере тесты не запускаются). Откат — git revert;
дельта `repl-control` синхронизируется вместе с `init-current-system`.
