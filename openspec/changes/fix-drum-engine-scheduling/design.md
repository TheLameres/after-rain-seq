# Design

## Context

`DrumEngine` — единственный движок проекта, не прошедший перевод на
lookahead-планировщик: `tick()` на каждом TICK дергает `DrumTrack.generate()`
(весь бар, паттерн-относительные биты) и кладёт всё в очередь немедленно;
Transport доставляет сразу. Capture приёмки `add-drum-pattern-api` показал
285 608 note_on (19 событий/бар × 15 032 тика) и 0 note_off. `MelodicEngine`
уже решает ту же задачу через `BeatScheduler` (C6): watermark, окно
`[watermark, now + H)`, доставка однократно в свой бит, пары note_on/note_off,
`reset()` на STOP. Код стабилен: 1945 passed, база линтеров удержана.

## Goals / Non-Goals

**Goals:**

- Каждый удар — ровно один раз, в свой абсолютный бит; пары note_on/note_off.
- Реакция на правку паттерна (мутация, pad-грид, `set_drum_pattern`,
  undo/recall) не хуже сегодняшней — применение сразу.
- Поведение mute (§4.6), порта (`port_label=None`, `set_port_label`),
  all_notes_off — не ломаются; свинг остаётся в Transport.
- Минимальный дифф: правки в `DrumEngine`, START/STOP-ветке хука
  `application.py` и одна точечная правка модели — `drum_track.py:136`
  (шаг сетки — фиксированная 16-я; ревизия §9, вскрыта тестами).

**Non-Goals:**

- Вынос свинга из Transport (двойное применение — известный техдолг AGENTS.md).
- Финализация change `add-drum-pattern-api` (её блок 9 делает тестер отдельно).
- Оконная генерация на уровне модели (новые методы `DrumTrack`), пересмотр
  outbox-семантики §4.5, правки MutationEngine и Push 2 UI.
- Изменение `BeatScheduler` (если не понадобится — см. решение 1).

## Decisions

### 1. Переиспользуем `BeatScheduler`, новый класс не вводим

`BeatScheduler` (`src/session/engine/beat_scheduler.py`) — generic:
хранит `TransportEvent` с абсолютным `beat`, `due()` изымает наступившие,
`cancel_from`/`rewind_to` поддерживают перестройку расписания, `reset()` —
сброс при STOP. Ничего мелодического в нём нет. `DrumEngine` получает поле
`_scheduler: BeatScheduler` и повторяет контракт `MelodicEngine.tick()`.
Импорт `src.session.drum.drum_engine → src.session.engine.beat_scheduler`
цикла не создаёт: `beat_scheduler` импортирует только `sync.transport_event`,
а `session.engine` не импортирует `session.drum` (проверяется задачей 1.1
grep'ом и тестом импортов, если такой есть).

### 2. Генерация циклами — через существующий `generate()`, без новых методов модели

Цикл паттерна — `cycle_len = steps / 4` битов (16→4, 32→8, 48→12, 64→16).
Достройка окна в `tick()`:

```
target = current_beat + horizon
while watermark < target - 1e-9:
    k = floor(watermark / cycle_len)          # цикл, содержащий watermark
    cycle_start = k * cycle_len
    for ev in self._track.generate():   # весь цикл, rel-биты 0..cycle_len (§9)
        abs_beat = cycle_start + ev.beat
        if abs_beat >= watermark - 1e-9:       # уже покрытое — не планируем
            schedule(note_on(abs_beat) + note_off(abs_beat + ev.duration))
    advance(cycle_start + cycle_len)
```

- **Почему так:** `generate()` остаётся единственной точкой итерации по
  lane'ам и выбора velocity (`_velocity_for_cell`); движок остаётся «мостом»
  (его роль по docstring) — только маппинг rel→abs и фильтр окна. Модель
  меняется точечно (шаг сетки, ревизия §9), новых методов не появляется,
  дифф остаётся минимальным.
- **Покрытие цикла генерацией:** при фиксированном шаге 0.25 (§9) rel-биты
  `generate()` покрывают ровно `steps·0.25 = steps/4 = cycle_len` — окно
  и цикл сходятся на любой сетке. До ревизии §9 формула позиций
  (`1.0/(steps/4)`) давала span 4 бита при любом steps, тогда как движок
  циклил через `steps/4` (8 при steps=32) — вторая половина цикла молчала;
  именно это противоречие вскрыли тесты `test_grid_32_and_64`.
- **Outbox §4.5 сохраняется с оговоркой:** `generate()` очищает и заново
  наполняет outbox при каждом вызове (`drum_track.py:108`); после change это
  происходит на построение окна — раз на цикл, а не на каждый тик. Иначе
  говоря, outbox обновляется реже (содержимое всегда соответствует последнему
  циклу паттерн-относительных событий), а не «как раньше», но семантика
  §4.5 (`current()`/`history()` по outbox) не меняется; тест
  `test_muted_track_sends_nothing` (outbox наполнен при mute) остаётся
  осмысленным после ревизии.
  В продакшене потребителей outbox drum-дорожки нет (проверено: `current()`/
  `history()`/`last_event` в `src/` не вызываются) — семантика outbox не
  критична, но менять её не нужно.
- **Velocity:** катится один раз на построение окна, а не на каждый тик —
  побочный фикс (сегодня 15k лишних бросков ГПСЧ на бар).
- **Окно и горизонт:** окно достраивается циклами — каждый проход планирует
  весь цикл, поэтому pending может превышать `now + horizon` вплоть до границы
  цикла (при steps=32/48/64 — на 8/12/16 битов). Функционально безвредно:
  `due()` доставляет однократно в свой бит, `cancel_from`/`rewind_to`/`reset()`
  от горизонта не зависят. Альтернатива — срез планирования по `target` —
  отвергнута: watermark должен дойти до границы цикла, и корректный срез
  потребовал бы per-cycle курсора («внутри цикла достроено до X») — новое
  состояние движка без функционального выигрыша (в отличие от melodic, где
  срез по границе ступени нужен для переключения прогрессии, у drum таких
  границ нет — мутация применяется на границе цикла целиком).
- **Фильтр `abs_beat >= watermark`:** первый тик после `ensure(now)` (и любой
  ребилд с середины цикла) не планирует удары в прошлом — они либо уже
  сыграны, либо будут отброшены как опоздавшие (`due()` режет всё старше
  1/16 бита, как у melodic).

### 3. Note_off: пара на `beat + ev.duration`

Каждый note_on дополняется `TransportEvent.note_off(note, beat=abs_beat +
ev.duration)` (`DEFAULT_GATE = 0.25`). Пара планируется атомарно в
`schedule()` — в capture появляются парные события, синтезатор не держит
ноты. Поле `duration` у note_on сохраняется (информационное; Transport
использует его только для свинга). Свинг по-прежнему живёт в Transport и
сдвигает только onset NOTE_ON — note_off не сдвигается, пара сохраняет длину
(то же поведение, что у мелодических нот); отложенные свингом события
обслуживаются `_held`-механизмом Transport без изменений.

### 4. Реакция на правку паттерна: fingerprint + `cancel_from(current_beat)`

Правки lane-паттернов и mute lane'ов приходят из четырёх мест (pad-грид,
`set_drum_pattern`, мутация на границе цикла, undo/recall) — все меняют
`lane.pattern`/`lane.muted` напрямую, сигнала движку нет. Решение — дешёвый
детект на каждом тике **до** достройки окна:

```
fingerprint = (track.snapshot(), tuple(l.muted for l in track.lanes))
```

`DrumTrack.snapshot()` уже существует (история версий) — кортеж кортежей
16×steps int'ов, сравнение копеечное даже на сетке 64. При изменении:

1. `scheduler.cancel_from(current_beat)` — снимает все запланированные вперёд
   note_on (метод режет `NOTE_ON` с `beat >= boundary - epsilon`, т.е. включая
   удар ровно на текущем бите);
2. `scheduler.rewind_to(current_beat)` — watermark на текущий бит;
3. достройка окна заново из текущего паттерна (решение 2) — оставшаяся часть
   текущего цикла и дальше играются по-новому; уже звучащие ноты доигрывают
   (их note_off остаются в pending — `cancel_from` не трогает note_off;
   лишний note_off на GM-барабане безвреден).

Тонкость границы (проверена на бумаге): мутация применяется в dispatch-хуке
до тиков движков (`application.py:513` → `:518`), поэтому на тике правки
`cancel_from(current_beat)` снимает и удар ровно на границе цикла
(`beat >= current_beat - epsilon`), а ребилд с фильтром `>= watermark`
возвращает его ровно один раз — дубля на границе нет. Это тот же механизм
B2 у `MelodicEngine` (`cancel_from(boundary)` + `rewind_to`), только граница
— текущий бит, а не будущая ступень.

Порядок в `tick()` — зеркально melodic: fingerprint-детект → ранний `return 0`
при `port_label is None` (**до** `ensure()` — планировщик не движется, как у
melodic; после re-route watermark отстаёт, окно достраивается от него,
опоздавшее более 1/16 отбрасывается) → `ensure()` → достройка окна →
mute-чек — **после** достройки (планирование идёт, доставка нет — §4.6) →
`due()` и доставка.

### 5. Выравнивание циклов с MutationEngine

Границы циклов — `k * (steps/4)` от нуля таймлайна. Это совпадает с
`MutationEngine._cycle_index(beat, cycle_beats) = floor(beat / cycle_beats)`
(`src/session/mutation/mutation_engine.py:47`): drum-мутация применяется на
первом тике нового цикла, fingerprint-детект подхватывает её в тот же тик.
Отдельной синхронизации не требуется; задача 3.3 фиксирует поведение тестом.
Выравнивание достигнуто ревизией §9: до неё формула позиций `generate()`
(шаг `4/steps`) и граница мутации (`steps/4`) расходились при steps≠16 —
латентный баг границы мутации; после ревизии оба равны `steps/4`.

### 6. Сигнатура `tick(current_beat, bpm)` сохраняется

Аргумент `bpm` сегодня не используется в теле (наследие автономной мутации,
удалённой в ветке ручной мутации); сохранение сигнатуры не трогает хук TICK
(`application.py:519`) и существующие тесты — дифф меньше. Docstring
исправляется (про «дорожка пересчитывает интервал мутации» — ложь). Если
когда-нибудь bpm понадобится — отдельная change.

### 7. `reset()` и START/STOP-ветка хука

Новый публичный `DrumEngine.reset()` — `scheduler.reset()` (по образцу
`MelodicEngine.reset()`). В `application.py` в ветки START и STOP
dispatch-хука добавляется `for engine in drum_engines: engine.reset()` рядом
с melodic (сейчас только `melodic_engines`, строки 522–534). После STOP
запланированное «прошлое» не доставляется; звучащие ноты глушит уже
существующий `transport.all_notes_off()`. `all_notes_off()` движка также
получает `scheduler.reset()` (как у melodic) — panic не оставляет pending.

### 8. Тест-стратегия

- **Unit (`tests/test_drum_engine.py`, ревизия):** луп последовательных тиков
  таймлайна (480 PPQN) на 2+ цикла → каждый активный шаг доставлен
  ровно один раз на абсолютной позиции; пары note_on/note_off (+0.25);
  эталон позиций `examples/drum_dub.py` (kick 0/3/4/7, snare 4/12,
  closedhat чётные, shaker 0/6/12, conga 6/14 — как `REFERENCE` в
  `spikes/spike_midi_dump.py`); правка паттерна/линейного mute между тиками
  → применяется с текущего тика без дублей; mute дорожки (тишина, outbox
  наполняется, unmute → возврат в такт); порт None → тишина, re-route →
  доставка на новый порт; all_notes_off; queue full; int-конвертация.
  Стиль — по `TestBeatScheduling` из `tests/test_melodic_engine.py`
  (on_map/off_map по битам, дренаж очереди после каждого тика).
- **Интеграция хука:** START/STOP → `drum_engines` получают `reset()` — по
  образцу hook-тестов `tests/test_midi_clock_in.py` (STOP: тиков после STOP
  нет, всё глушится сразу).
- **Сквозной (capture):** прогон нескольких циклов через Transport с
  CaptureRecorder (по образцу `tests/test_engine_control_capture.py`) →
  в capture нет дублей одной ноты на одном тике, каждому note_on
  соответствует note_off, позиции совпадают с эталоном drum_dub. Это
  программный аналог ручного разбора `spike_midi_dump.py --drum-dub`.

### 9. Ревизия (post-implementation): шаг сетки — фиксированная 16-я (0.25 бита)

Тесты реализации (`test_grid_32_and_64`) вскрыли внутреннее противоречие
первой редакции design: позиции брались из `DrumTrack.generate()`
(`drum_track.py:136`: `step_duration = 1.0 / (self.steps / 4)` = `4/steps`
бита — паттерн любого steps укладывался в 4 бита), а `cycle_len` — из
MutationEngine (`steps/4`). При steps=32: 32 × 0.125 = 4 ≠ 8 — генерация
покрывала половину цикла, вторая молчала; мутация и движок расходились.

**Решение (зафиксировано пользователем):** семантика «16-е ноты фиксированно»
— `step_duration = 0.25` бита всегда, независимо от steps; цикл паттерна —
`steps/4` битов (32 шага = 2 такта, 64 = 4 такта). Согласуется с
MutationEngine, спекой и тестами.

- **Мотивировка:**
  - `MutationEngine` уже использует границу `steps/4`
    (`mutation_engine.py:60`, `engine_control.py:513-517` — cycle_beats
    фасада) — модель должна совпадать с движком мутации, а не наоборот;
  - спека capability и дельта описывают цикл через `steps/4`;
  - музыкально: 16-е ноты — стандарт сетки dub techno (эталонные позиции
    `examples/drum_dub.py` и `spike_midi_dump.py REFERENCE` заданы в
    16-сетке такта);
  - при steps=16 поведение не меняется вовсе (`1.0/(16/4) = 0.25`).
- **Правка модели (точечная):** `drum_track.py:136` — `step_duration` с
  `1.0/(steps/4)` на `0.25`; комментарий `# доля = 1/4 такта` исправить
  (доля = 1/16 такта = 0.25 бита). Задача 1.5.
- **Отвергнутая альтернатива:** «32-е в такте» — шаг `4/steps`, цикл 4 бита
  при любом steps. Следствия: граница drum-мутации (`steps/4`) перестала бы
  совпадать с границей паттерна — мутация «на границе цикла» рвала цикл
  пополам при steps=32 (латентный баг границы мутации); расхождение со спекой
  и с уже написанными тестами; музыкально — удары эталона drum_dub при
  steps>16 сжимались бы в один такт, ломая метрику примера.
- **Аудит потребителей семантики steps (проверено графом graphify + grep по
  коду):**
  - `MutationEngine._cycle_index` + `AppEngineControl` cycle_beats
    (`engine_control.py:513-517`, `mutation_engine.py:60/151`) — `steps/4`;
    совместимо, это эталон решения;
  - `DrumEngine` (`drum_engine.py:189`, `cycle_len = steps/4`) — совместимо;
    после правки модели окна движка совпадают с генерацией ровно;
  - `DrumPatternCompiler.compile(pattern, track.steps)` — пошаговый,
    длительность шага в битах не читает; нотация разворачивается на весь
    цикл (шаги 0..steps-1). Документационный нюанс: «весь бар» в README
    (`README.md:335/348`) и в комментарии `examples/drum_dub.py` точен для
    steps=16 (цикл = такт); при steps≠16 «бар» фактически означает «цикл»
    (2/3/4 такта) — формулировка уточняется задачей 1.6 (только текст, код
    компилятора не меняется);
  - `DrumLane.ensure_length` (`drum_lane.py:32`) — только длина списка
    паттерна, биты не читает — совместимо;
  - пад-грид Push 2 (редактирование ячеек) — **не реализован** (план D3 в
    ROADMAP; `_handle_pad` работает только на экране VERSIONS — выбор
    дорожки/recall; docstring: «Пады других режимов — D3»). Допущений о
    длительности шага нет; при будущей реализации D3 сетка остаётся
    шаг-индексной — зависимостей не найдено;
  - REPL-команды смены steps — отсутствуют (grep по `src/repl` пуст);
    смена сетки в рантайме не предусмотрена — совместимо;
  - дисплеи TRACKS/GEN (`screens.py`) — шаги не рисуют (только
    профиль/канал/счётчик мутаций) — совместимо.
- **Следствие:** при steps≠16 меняются только длительность цикла
  (`steps/4`) и плотность шагов (всегда 16-е); абсолютная позиция удара —
  `step × 0.25` внутри цикла `steps/4`.

## Risks / Trade-offs

- [Опоздавшие удары после потери тиков] → `due()` режет события старше 1/16
  бита — удар пропускается, а не играется пачкой. Минимальный интервал сетки
  при фиксированном шаге — 0.25 бита, порог опоздания (1/16) меньше него:
  после сбоя тиков пропускаются только удары, отставшие более чем на 1/16
  бита. Принимаем: семантика идентична melodic, потеря тиков — нештатный
  путь.
- [Float-дрейф] → шаг сетки всегда 0.25 бита (диадический), `cycle_len`
  — целые (4/8/12/16); дрейф внутри сетки исключён, epsilon 1e-6 планировщика
  и сравнения в фильтрах (1e-9 в melodic-стиле) покрывают накопление
  watermark на горизонте; тесты сравнивают биты через `pytest.approx`.
- [Сравнение snapshot() на каждом тике] → 16×steps int'ов (≤ 1024) на каждый
  тик таймлайна (480 PPQN) — незначимо; альтернатива (счётчик ревизий на
  дорожке) требует
  правки модели и всех точек правки — отвергнута ради минимального диффа.
- [Гонка REPL-потока ↔ dispatch-хук] → правки `lane.pattern` из REPL-потока
  читаются движком в потоке тиков; exposure тот же, что у melodic
  (`pending_degrees`) и сегодняшнего drum (generate() из потока тиков).
  GIL делает чтение списка атомарным на уровне элементов; worst case —
  правка видна на тик позже. Не усугубляется этим change'ом.
- [Дрейф спек от кода] → дельта формулирует внешне наблюдаемое поведение
  (доставка, пары, реакции); имена классов/полей — только в design/tasks.

## Root cause падения hook-тестов (не устранён)

**Статус решения (2026-11-19):** пользователь решил остановиться **без
применения фикса** — циклы правки кодера исчерпаны (2/2). Два hook-теста
остаются падающими как известная проблема с задокументированным root cause
и готовым фиксом на будущее.

### Симптом

- `tests/test_drum_engine_hook.py`: `test_restart_starts_from_zero_phase`
  — 0 note_on вместо 1; `test_ticks_deliver_once_per_beat` — `[]` вместо
  `[0.0, 4.0]`.
- `test_stop_clears_drum_scheduler` — зелёный (ассерт по
  `pending_count > 0`, delivery не проверяет).

### Root cause (установлен, подтверждён статическим анализом всей цепочки)

Production-дефект повторной инициализации в `App._init_clock_manager`
(`src/app/application.py:438`):

1. `App.__init__` (`application.py:188-189`) вызывает
   `self._clock_manager.start()` → внутренний клок-источник CM #1
   запускается, воркер TickProxy #1 (стартованный в `_init_clock_manager`
   #1, строка 553) тикает в реальном времени постоянно.
2. Тест (`tests/test_drum_engine_hook.py`, `_app_with_drum`) подменяет
   очередь/сессию и вызывает `_init_clock_manager(_Cfg())` повторно.
   Хук #1 захватил в closure тот же список `self._drum_engines`
   (`application.py:504`), тест делает `app._drum_engines.append(engine)`
   (строка 77) — мутация того же объекта, поэтому тестовый движок тикается
   из ДВУХ потоков.
3. Воркер #1 тикает движок с `timeline1.current_time` (Timeline #1 ушла
   далеко вперёд с `__init__`); первый тик воркера делает
   `ensure(timeline1.current_time)` → водяной знак BeatScheduler становится
   большим числом.
4. Тест тикает вручную через hook #2 с `timeline2.current_time` (стартует
   с 0.0, +1/480 за тик) — тестовые `now` никогда не достигают
   запланированных битов → `due()` пусто → очередь пуста → CaptureRecorder
   пуст.
5. Melodic-тест (`tests/test_midi_clock_in.py`) не падает, потому что его
   ассерты про позицию таймлайна, а не про delivery через recorder.
6. В проде `_init_clock_manager` зовётся один раз — дефект не проявляется;
   guard переиспользования очереди (строки 458–459) показывает, что
   повторная инициализация предусмотрена, но старый клок/воркер не гасятся.
