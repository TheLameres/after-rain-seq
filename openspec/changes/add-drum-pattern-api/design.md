# Design

## Context

План G2 дал скриптам фасад `ScriptSession` над `EngineControl`, ручная мутация
(`docs/mutation-manual-spec.md`) дала drum-дорожкам линейную историю версий
(`DrumTrack.snapshot()/restore()`, `VersionHistory`, `MutationEngine`), но
запись в drum-сетку извне по-прежнему одна: пад-грид Push 2. `create_drum_track`
из REPL недоступен (REPL-команды домена `drum` нет — creation живёт только в
`screen_controller` и скриптах), а паттерн lane'а не задаёт ни один внешний
интерфейс. Код стабилен: 1945 passed, база линтеров удержана.

## Goals / Non-Goals

**Goals:**

- Строка-нотация → ячейки lane-сетки (0/1/2), с евклидовым ритмом как
  гражданином нотации; компилятор — чистый модуль слоя `session.model`.
- Один метод фасада `EngineControl.set_drum_pattern` — общий вход для REPL и
  скриптов (правило «единственный фасад» из спеки repl-control).
- Ручная правка паттерна → новая версия в `VersionHistory`; undo/recall
  работают после REPL/скриптовых правок.
- Исполняемый пример `examples/drum_dub.py` + раздел README.

**Non-Goals:**

- Оператор вероятности `?` и альтернатива `a|b` (решение ниже — отложены).
- Вложенность и относительные длительности Strudel (`[]`, `<>`, `*`, `/`, `@`,
  `!`, polyrhythm через `,`) — не ложатся на фиксированную сетку (решение ниже).
- Смена числа шагов сетки (`steps`) из нотации; mute lane'а из нотации.
- Push 2 UI для паттернов (пад-грид уже покрывает редактирование с железа).

## Decisions

### 1. Имена: метод `set_drum_pattern`, REPL-домен `drum`

- Метод фасада: `set_drum_pattern(name: str, lane: str, pattern: str) -> EngineResult`.
  Имя согласуется с существующими `set_track_*` методами; `pattern` — сырая
  строка нотации (компиляция — забота реализации, не вызывающего).
- REPL: новый домен `drum` с двумя командами:
  - `drum add [name]` → `create_drum_track(name)`;
  - `drum pattern <track> <lane> [<notation…>]` → `set_drum_pattern`
    (без нотации — очистка lane'а, см. §9).
- **Найденный пробел:** сейчас REPL не может создать drum-дорожку вообще
  (`track add` — только melodic-профили; `create_drum_track` дёргают
  `screen_controller` и скрипты). Критерий приёмки «создать drum-дорожку из
  REPL» требует `drum add` — включено в скоуп.
- Альтернатива `track add drum` отвергнута: профильный реестр `PROFILES` —
  melodic-only, подмешивать служебное слово в него грязно; отдельный домен
  `drum` даёт место для будущих drum-команд (mute, steps) и читается в help.

### 2. Грамматика нотации v1

Формально (компилятор — нисходящий разбор, без регулярок на всю строку):

```
notation  := cells | euclid
cells     := cell*
cell      := "x" | "X" | "." | "~"
euclid    := "(" pulses "," segs [ "," offset ] ")"
pulses, segs, offset := целое
игнорируется: пробел, "|"
```

- `x` = норма (ячейка 1), `X` = акцент (2), `.` и `~` = выкл (0) — два синонима
  реста, `~` привычен Strudel-аудитории, `.` — классическая drum-нотация.
- Пробелы и `|` — визуальная группировка (тактовая черта), на компиляцию не
  влияют: `x..x|x..x|....` ≡ `x..xx..x....`. Регистр ячеек значим (`x` ≠ `X`),
  остальные токены — нет.
- Пустая нотация (после выброса разделителей) = очистка lane (все нули) —
  легальный способ сбросить lane без Push 2.
- Евклид-группа `(p,s)` — **p ударов на весь цикл (бар)**: сетка `steps`
  делится на `s` равных сегментов, удар ставится на старт сегмента. Базовый
  bjorklund-паттерн длины `s` (какие из `s` сегментов активны) строится
  переиспользованием `PEuclideanCached` (тот же слой,
  `src/session/model/euclidean.py`) — компилятор не дублирует `_bjorklund`;
  затем сегменты растягиваются на сетку: позиция сегмента `i` на сетке
  `idx_i = (i * steps) // s` (floor), ячейка `idx_i` = `base[i]` (0/1).
- Мотивировка: буквальное разворачивание `(p,s)` в `s` ячеек с паддингом
  (первая редакция design) давало «трещотку» в первой половине бара и тишину
  во второй — `(3,8)`@16 бил в шаги 0, 3, 6; найдено падающим тестом
  `test_full_pulses` и живым MIDI-трейсом на приёмке. Решение (согласовано
  с пользователем): `(p,s)` описывает весь бар — `(3,8)`@16 бьёт в 0, 6, 12
  (интервал 1.5 бита), `(8,8)`@16 — восьмые `0, 2, …, 14`, то есть
  `[1,0]×8`, а НЕ `[1]×16`: восемь сегментов на 16 шагов — это восьмые
  ноты, сплошная сетка была бы `(16,16)`.
- Краевые случаи (точные правила):
  - `steps % s != 0` → позиции по формуле `idx_i = (i * steps) // s`,
    детерминированно: `(5,5)`@16 → шаги 0, 3, 6, 9, 12. Коллизий нет при
    `s ≤ steps`: соседние позиции отличаются минимум на
    `floor(steps / s) ≥ 1`, выход за сетку исключён (`idx_{s-1} ≤ steps-1`).
  - `s > steps` → ошибка (сегментов больше, чем шагов сетки).
  - `p = 0` → все нули (легальная очистка); `p = s` → удар на старте каждого
    сегмента; `p > s` → ошибка (как раньше).
  - Смесь литеральных ячеек и евклида в одной строке → **ошибка**
    («euclid group must be the only element»): семантика «на весь бар»
    несовместима с конкатенацией — у евклида больше нет собственной длины
    в ячейках, а наложение/поддиапазоны потребовали бы новой семантики
    (тот же класс сложности, что отложенная вложенность Strudel, §4).
- Третий аргумент `offset` — сдвиг вправо по времени (roll), применяется к
  номерам сегментов **до** растягивания: ячейка сегмента `i` берётся как
  `base[(i - offset) mod s]`. `(3,8)`@16 → удары на 0, 6, 12; `(3,8,1)`@16 →
  удары на 2, 8, 14. Валидация: `0 ≤ offset < s`, иначе ошибка.
- Семантика длины для литеральной части (когда евклида в строке нет):
  итог длиннее `track.steps` — **ошибка** (не обрезаем молча); короче —
  паддинг нулями до сетки (остаток такта молчит). Пример на сетке 16:
  `x.x.` → ячейки 0–3, далее тишина.

Примеры (сетка 16):

| Нотация | Ячейки / удары |
|---|---|
| `x..x|x..x|....|....` | kick four-on-the-floor с пропуском |
| `X..x X..x X..x X..x` | акцент на 1, норма на 5/9/13 |
| `(3,8)` | удары на шагах 0, 6, 12 (интервал 1.5 бита) |
| `(8,8)` | восьмые: шаги 0, 2, 4, …, 14 → `[1,0]×8` |
| `(4,4)` | четверти: шаги 0, 4, 8, 12 |
| `(5,5)` | неравномерное деление: шаги 0, 3, 6, 9, 12 |
| `(3,8,1)` | удары на шагах 2, 8, 14 (сдвиг на 1 сегмент) |
| `x.x. (2,8)` | ошибка: смесь литералов и евклида |
| `` (пусто) | очистка lane |

### 3. Операторы `?` (вероятность) и `|` (альтернатива) — отложены

- `?` / `?0.3` (Strudel случайно выбрасывает событие): **не включаем в v1**.
  Сетка статична и хранит ячейки 0/1/2; вероятность требует либо (а) броска
  кубика в `generate()` — рендер перестаёт быть детерминированной функцией
  ячеек, ломая семантику версии (снапшот хранит ячейки, а звучание каждый
  цикл разное — undo «вернул тот же бит» становится ложью), либо (б)
  расширения ячейки полем вероятности — каскад через `DrumLane`,
  `DrumEngine`, пад-грид Push 2, velocity-уровни. Оба варианта неоправданны
  для v1; если позже понадобится — отдельная change с расширением модели
  ячейки, а не хак в компиляторе.
- `|` как оператор альтернативы `a|b`: **не включаем**, `|` занят визуальной
  группировкой (решение 2). Альтернатива — тот же класс проблем, что
  вероятность (выбор на цикл требует состояния вне снапшота), плюс конфликт
  с уже привычной трактовкой тактовой черты. Если когда-нибудь понадобится —
  другой сигил (Strudel-стиль `<>`), в отдельной change.
- Оба решения фиксируются в tasks как явные non-goals компилятора, чтобы
  ревью не «додумывало» их в реализацию.

### 4. Не переносим вложенность/относительные длительности Strudel

Модель проекта — фиксированная сетка 16/32/48/64 шагов, ячейка 0/1/2, каждый
удар — one-shot с фиксированным gate (`DEFAULT_GATE = 0.25`). У сетки нет
понятия относительной длительности (нет сустейна), у ячейки — нет суб-шагов;
`[]`/`*`/`/`/`@`/`!` осмысленны только поверх слой-модели с длительностями и
вложенными событиями, которой здесь нет. Компилятор, натягивающий их на
ячейки, создал бы ложное ощущение выразительности (например `x*2` = `xx`?
а `xx/2`?), не добавив музыкальных возможностей сверх литералов и евклида.
Подмножество выбрано так, чтобы каждый элемент грамматики честно ложится на
модель: ячейка — ячейка, евклид — распределение по сетке.

### 5. Компилятор: где живёт и как ошибается

- Файл `src/session/model/drum_pattern_lang.py`, публичный класс
  `DrumPatternCompiler` (правило «один класс — один файл»), статический метод
  `compile(pattern: str, steps: int) -> list[int]`. Слой `session.model`,
  импортирует только `euclidean.py` — вверх не тянет ничего; REPL/app/скрипты
  не компилируют сами (единственная точка компиляции — внутри фасада).
- Ошибки — `ValueError` с человекочитаемым русским сообщением и позицией
  символа (`"неожиданный символ 'k' в позиции 3"`). Это конвенция слоя
  (`session.create_drum_track`, `DrumLane.ensure_length` и др. кидают
  `ValueError`); `AppEngineControl` ловит `ValueError` → `EngineResult.fail`
  (как в `create_drum_track`), в скрипте при `fatal=True` это поднимается как
  `ScriptError`. Отдельный тип исключения не вводим — иерархия исключений
  здесь не даёт выигрыша, а `ValueError` уже часть контракта фасада.

### 6. Разрешение lane: индекс / GM-номер / имя

- `DrumTrack.resolve_lane(spec: str) -> int` (слой model, рядом с данными):
  целое 0–15 — индекс; целое 36–51 — GM-номер; иначе — имя lane'а
  (`"Kick"`, `"Snare"`, …) без учёта регистра. Всё прочее — `ValueError`.
- `_GM_DRUM_MAP` в `drum_track.py` становится публичной константой
  `GM_DRUM_MAP` (нужна main.py для провайдера автодополнения; переименование —
  чисто техническое, поведение не меняет).
- Индексы и GM-номера различимы диапазонами (0–15 vs 36–51) — двусмысленности
  нет.

### 7. VersionHistory: кто записывает версию и когда

- Применение паттерна — **сразу** (REPL/скрипт слышат результат мгновенно):
  `lane.pattern` заменяется новым списком целиком (одна ссылка — та же
  практика, что `set_track_channel` меняет `track.channel` из REPL-потока).
- Запись версии — **синхронно, движком, не моделью** (требование брифа и спеки
  mutation: снимки снимает `MutationEngine`). Новый публичный метод
  `MutationEngine.record_manual_version(track_name) -> bool`: снимок
  `DrumVersion(lanes=track.snapshot())` → `history.push()` →
  `_sync_counter()` — без шага дрейфа, в отличие от `_commit_manual`.
  Семантика — как у мутации: «состояние до правки уже лежит в истории
  предыдущей версией», поэтому в историю уходит состояние **после** правки.
- **Дедупликация**: перед push снимок сравнивается с текущей головой истории
  (`history.current`); совпадение → версия не создаётся, метод возвращает
  «без изменений». Повторная установка того же паттерна не плодит дубликаты
  версий (в отличие от `_commit_manual`, где шаг дрейфа гарантированно меняет
  состояние, здесь правка может быть идемпотентной). Сравнение дешёвое —
  снимок всё равно строится; возврат к старому паттерну после промежуточных
  правок честно создаёт новую версию (сравнивается только с головой, не со
  всей историей).
- **Регистрация drum-дорожки при создании** (закрытие найденного разрыва):
  сегодня `MutationEngine` регистрирует дорожки один раз — в
  `application._init_mutation` при старте и только при `mutation.enabled`;
  `session.create_drum_track` движок мутации не трогает. Следствие без правки:
  `drum add` (REPL) или `session.add_drum` (скрипт) → `drum pattern` → `undo`
  давало бы «track is not mutable» — критерий брифа не выполнялся бы для
  любых дорожек, созданных в рантайме. Решение: `AppEngineControl.create_drum_track`
  после успешного создания и маршрутизации регистрирует дорожку
  (`engine.register_drum_track(name, track)`), если движок мутации существует —
  симметрично уже существующему on-demand созданию DrumEngine
  (`application._create_engine_for`). Разрыв закрывается **только для drum**;
  melodic-дорожки, созданные после старта, остаются вне MutationEngine — это
  известный техдолг из AGENTS.md, вне скоупа. При `mutation.enabled=false`
  (движка нет) паттерн применяется без истории, в сообщении — note.
- Дорожка не зарегистрирована в `MutationEngine` → паттерн применяется, версия
  не пишется, в сообщении `EngineResult` — note. После решения о регистрации
  при создании это возможно только при выключенной мутации в конфиге
  (`mutation.enabled=false`) или недоступном движке — не в основном сценарии.
- Потоки: `EngineControl` вызывается из REPL-потока, `MutationEngine` тикает в
  main loop; пересечение возможно только на push/undo/recall в `VersionHistory`
  (составные операции над списком). Страховка дешёвая — `threading.Lock`
  внутри `VersionHistory` на `push/undo/recall`; очередь + отложенная запись
  на тике отвергнута: скрипт делает `set_drum_pattern` → `undo` синхронно
  подряд, отложенная запись ломала бы эту последовательность (undo сработал бы
  до того, как версия легла в историю).
- `undo`/`recall`/`history` в REPL после правок работают без изменений —
  механизм уже восстановит `lane.pattern` через `DrumTrack.restore()`.

### 8. Скриптовый фасад и валидатор

- `ScriptSession.set_drum_pattern(name, lane, pattern, *, fatal=True)` —
  обёртка 1:1 через `_call`, как остальные методы.
- Регистрации в `ScriptValidator._facade_methods` **не требуется**: таблица
  строится рефлексией `inspect.getmembers(ScriptSession)` — новый публичный
  метод попадает в линт автоматически (задача фиксирует это тестом: `script
  check` пропускает вызов с верной арностью и ловит неверную). Формулировка
  брифа «иначе валидатор не пропустит» верна лишь как следствие: без публичного
  метода на `ScriptSession` вызов действительно отвергается как unknown.

### 9. REPL-команды: разбор аргументов

- `drum add [name]`: `min_args=0, max_args=16, join_args=True` — имя с
  пробелами склеивается (конвенция `track delete`).
- `drum pattern <track> <lane> [<notation…>]`: `min_args=2, max_args=64`,
  `join_args=False`. Правила разбора в executor: `args[0]` — дорожка (имена
  с пробелами — в кавычках, как везде), `args[1]` — lane, `" ".join(args[2:])`
  — нотация; **два аргумента = очистка lane'а** (пустая нотация по грамматике
  §2) — иначе очистка была бы недостижима из REPL (в скрипте/фасаде пустая
  строка доступна и так). Пробелы внутри нотации легальны (грамматика их
  игнорирует), кавычки для нотации не обязательны, но рекомендуются в README
  при использовании `|`.
- Ошибки — обычный путь `CommandResult(code=1)` c текстом из `EngineResult`.

### 10. Автодополнение

- Статическое дерево пополняется автоматически из таблицы `CommandSpec`
  (домен `drum` с действиями `add`/`pattern`).
- Динамические контексты в `completer.py`: после `drum pattern` — имена
  дорожек (как у `track delete`), следующим токеном — имена lane'ов через
  новый провайдер `"lane"` (инжект из `main.py`, чтобы `repl/` не импортировал
  `session.model` — то же расслоение, что у провайдеров `"profile"`/`"scale"`).

## Risks / Trade-offs

- [Расширение ABC ломает заглушкам контракт] → новые методы `EngineControl`
  по прецеденту C1–C4 делаем **не абстрактными** с дефолтом
  `EngineResult.fail("...not supported by this control")` — существующие моки
  и стабы продолжают работать, тесты-заглушки не падают.
- [Гонка истории версий REPL-поток ↔ main loop] → lock в `VersionHistory`
  (решение 7); окно гонки и без него исчезающе мало (push в main loop — только
  при коммите pending-мутации).
- [Гонка `_sync_counter` из REPL-потока] → lock в `VersionHistory` защищает
  целостность списка версий, но `_sync_counter` (замена `MutationState` в
  `_states` и вызов `track.record_mutation`) из REPL-потока от гонки с тиком
  main loop не защищён; worst case — потерянный инкремент счётчика `mut:N` на
  дисплее до следующей мутации (само состояние истории корректно). Принимаем:
  риск косметический, отдельный lock на `MutationEngine` не вводим; если
  когда-нибудь понадобится строгий счётчик — отдельная change.
- [Нотация разъедется с пад-гридом] → компиляция только через фасад; пад-грид
  читает те же `lane.pattern`; расхождений нет по построению. Undo/recall
  после ручных правок покрывается интеграционным тестом.
- [Дрейф спек от кода] → дельты формулируют внешне наблюдаемое поведение
  (команды, сообщения об ошибках); имена классов — только в design/tasks.

(компилятор → модель → движок мутации → фасад → REPL → скрипты → пример →
README), регрессия и линтеры — на исполнителе (в этом конвейере тесты не
запускаются). Откат — git revert; спеки синхронизируются вместе с
`init-current-system`.
